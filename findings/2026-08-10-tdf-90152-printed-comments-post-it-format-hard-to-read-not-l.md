## Summary

When a Writer document with comments is printed/exported with comments enabled ("Print comments" → `PrintAnnotationMode`), LibreOffice builds a temporary "post-it document" and renders each comment as:

```
Page : 3 Line : 2 Author : Jane Doe 08.06.2013        <- header line
<comment text…>                                        <- body
```

This header is generated by `lcl_FormatPostIt()` in `sw/source/core/doc/doc.cxx`. It is a single flat, plain-text run whose punctuation and field order are hard-coded in C++; only the date is localized. That is the root cause of both complaints in the bug title: *hard to read* (no visual distinction between label and value) and *not locale-aware* (fixed English-style `" : "` separators and fixed Page→Line→Author→Date order).

## Fix proposal

All changes in `sw/source/core/doc/doc.cxx`, function `lcl_FormatPostIt` (555-604), plus one header include.

### 1. Locale-aware separators (core of "locale-aware")
- Delete L562 `static char const sTmp[] = " : ";`.
- Move `SvtSysLocale aSysLocale;` to the top of the header assembly and take the group separator from the locale:
  ```cpp
  SvtSysLocale aSysLocale;
  const OUString aListSep( aSysLocale.GetLocaleData().getListSep() ); // localedatawrapper.hxx:227-228 (already included at doc.cxx:58)
  ```
- Join the three groups (Page, Line, Author+date) with `aListSep` (English `", "`, other locales e.g. `"; "`) instead of hard-coded `" "`.
- Keep `" : "` (or better: drop it and make the label strings carry their own punctuation, e.g. `"Page:"`) as the label→value separator. Cleanest for translators: keep the labels as-is and use `" : "` literal only as label/value separator.

### 2. Readability — bold the labels
- Add `#include <editeng/wghtitem.hxx>` (SvxWeightItem; pattern already used in `sw/source/core/doc/DocumentStylePoolManager.cxx:181` with `RES_CHRATR_WEIGHT`, `hintids.hxx` already included at doc.cxx:45).
- Insert the header in label/value segments using the documented "empty hint" idiom (`IDocumentContentOperations.hxx:228-230`: on a collapsed selection `InsertPoolItem` inserts an attribute hint that applies to subsequently inserted text):
  ```cpp
  auto insertBoldLabel = [&](const OUString& rLabel) {
      pIDCO->InsertPoolItem(aPam, SvxWeightItem(WEIGHT_BOLD, RES_CHRATR_WEIGHT));
      pIDCO->InsertString(aPam, rLabel + " : ");
      pIDCO->InsertPoolItem(aPam, SvxWeightItem(WEIGHT_NORMAL, RES_CHRATR_WEIGHT));
  };
  // Page group, Line group (if nLineNo), Author+date group, joined with aListSep
  ```
- Result: `**Page** : 3, **Line** : 2, **Author** : Jane Doe 08.06.2013` — labels visually distinct from values and body.

### 3. (Optional enhancement) localized template for full order control
If translators should also be able to reorder Page/Line/Author/Date (e.g. date-first in some locales), add one resource, e.g. in `sw/inc/strings.hrc` next to STR_RESOLVED (767):
```cpp
#define STR_PRINT_POSTIT_FORMAT  NC_("STR_PRINT_POSTIT_FORMAT", "Page : %1 Line : %2 Author : %3 %4")
```
and build via `SwResId(STR_PRINT_POSTIT_FORMAT).replaceFirst("%1", …)` … `.replaceFirst("%4", …)`. This is the classic easyHack "locale-aware format string" approach; it requires .po/Weblate turnover but is low-risk.

## Risks

1. **Page-count regression**: only character attributes + separator text change (no extra paragraphs), but a longer header (list separator + bold) could wrap on narrow pages with very long author names → post-it page count could grow; the proposed unit test guards this.
2. **`getListSep()` edge cases**: some locales return unusual/empty separators; fall back to `", "` if empty.
3. **Empty-hint bold idiom**: relies on `DocumentContentOperationsManager` honoring the hint for the immediately-following `InsertString`; verify in the test (assert `CharWeight`).
4. **Translator overhead** (if Option 3 chosen): new `NC_` string must be translated; strings.hrc changes touch all locales via Weblate — acceptable, standard for easyHacks.
5. **No existing tests break** — verified no test asserts the current header text.
